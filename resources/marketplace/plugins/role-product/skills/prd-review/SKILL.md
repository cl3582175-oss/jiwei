# 需求文档审阅

需求审阅要找会让实现和验收走偏的缺口。按固定清单检查，只报告有依据的问题，让作者知道具体该补哪一句或哪条流程。

## 步骤

1. **确认范围与版本**

   - 取得用户指定 PRD，用 note_read 或 source_read 阅读可用正文。
   - 记录版本、目标读者和本次要审的范围，缺附件明确说明。
   - 不把未读页面推断为缺失；必要时先请求对应章节。

2. **核对目标、用户与范围**

   - 检查目标和成功指标是否可衡量，指标是否有基线与时间窗口。
   - 检查目标用户与场景是否具体，能否描述谁在何时做什么。
   - 检查做什么与不做什么，范围有冲突时引用双方原句。

3. **核对完整业务流程**

   - 逐项看主流程、空状态、失败、权限和并发。
   - 用具体触发条件说明缺口会造成什么行为不确定。
   - 不是所有功能都需要复杂并发策略；不适用项不硬凑问题。

4. **核对数据和上线**

   - 检查埋点、计算口径、数据来源与指标是否对应。
   - 检查上线、灰度、回滚和数据兼容性是否说清。
   - 检查依赖与风险，区分需要决策的阻塞和可以后补的说明。

5. **按严重程度写问题**

   - 只输出问题，按阻塞、重要、建议排序。
   - 每条包含位置、缺什么、影响和一条具体补写建议。
   - 同一根因合并，不用重复条目夸大问题数量。

6. **让作者可以接着改**

   - 先指出会阻止实现或验收的项，其余简短列出。
   - 没有发现问题就说明在已读范围未发现，并列未读材料。
   - 用户要求保存时才确认笔记，用现有提案工具写入，不擅自重写整份 PRD。

## 产出

- 按阻塞、重要、建议排序的问题清单。
- 每条包含原文位置与具体触发条件。
- 说明实际影响和可直接采用的补写建议。
- 标明未读、缺材料及待决策项。
- 只报告问题，不附通用赞美或无关清单。

## 不要做

- 不要没有证据地评价作者能力。
- 不要把未读内容当成遗漏。
- 不要只写“需要完善”不给具体建议。
- 不要未经要求替换整个需求方案。

## 示例

用户：帮我审这份 PRD。
助手：把文档或笔记选给我，并说明当前版本。我会按目标、用户、范围、流程、数据、上线和风险检查，只列问题与具体补写建议。

用用户使用的语言回答。
