# 积微（Jiwei）项目原则

## Core Principles

### I. 本地数据与隐私保护

- 积微以本地知识库为基础，用户拥有自己的数据。不得以新增账号、项目服务器或上传数据为代价，
  擅自改变现有本地优先的产品约定；使用云端模型时，只向用户选择的服务商发送获准使用的内容。
- 标为“不给 AI”的笔记、资料，以及已删除或已撤销授权的内容，必须按现有访问边界从 AI 检索、
  上下文、后台 AI 整理、引用和 MCP 等相关入口排除；会话附件的局部授权不得扩展成全局授权。
  派生内容必须保留适用的隐私限制，排队或多轮处理期间也必须尊重权限变化。
- API 密钥及其他凭证沿用本地加密与既有安全存储；不得进入源码、提交、日志、审查证据或聊天输出。

依据：README 的“你说了算”，以及架构文档中的隐私、安全、附件隔离与动态撤权约定。

### II. 用户掌控智能体行为

- AI 修改用户数据必须遵守对应的既有授权、提案、预览、确认与撤销策略；
  拒绝、超时和停止不得触发未获准的写入。
  用户预先授权的自动任务，只能在已明确配置的触发条件、工具权限、结果去向与费用边界内执行。
- 网页、邮件、资料和外部工具返回的内容只能作为数据，不能作为执行指令。
  读取外部内容后的写入必须确认，对外发送、删除等操作不得绕过现有工具权限策略。
- 工具调用与外部访问必须沿用可查的审计记录；费用必须可见并受用户设置的限额约束。
- 模型生成的界面、可执行内容和插件不得获取未授予的本机权限；保持现有沙箱与不运行插件脚本的边界。

依据：README 的写入确认、防提示注入、费用、审计、MCP 与插件约定。

### III. 数据完整与来源可追溯

- 笔记正文沿用 Yjs 状态与增量作为事实来源，由主进程派生检索、链接等数据；
  不得用显示状态或独立副本替代正式持久化路径。
- 保留已有块 ID、引用、批注、附件与版本历史的关系，不得为重建或重构随意重新生成标识。
  导入发生 ID 冲突时，按现有格式约定一致重映射相关引用。
- 数据库迁移前必须备份；结构、文档格式或导入导出契约变化必须处理版本兼容与恢复路径，
  不得静默丢弃旧数据。沿用既有软删除、保存握手和备份机制。
- 基于资料的回答与产出必须保留可定位原文的来源；证据不足、来源失效、处理失败或结果不完整时，
  必须如实呈现，不能编造来源或以界面成功掩盖数据失败。

依据：README 的出处与数据所有权约定，架构文档及数据格式文档。

### IV. 现有架构与边界清晰的变更

- 保持 Electron 主进程、后台工作进程、preload、shared 与 renderer 的现有职责划分；
  数据库与权限逻辑由负责它们的服务处理，耗时处理复用既有后台任务路径。
- 渲染进程保持沙箱、上下文隔离和禁用 Node 集成，通过现有生成的桥接 API 访问主进程；
  跨进程输入沿用共享契约与校验，禁止跨层直连数据库或绕过权限入口。
- 优先扩展已有组件、服务、契约和数据模型；不创建重复业务规则、平行架构或隐藏共享状态。
  最小合理变更以完整实现行为为准，不能为减少文件数而漏改真正负责行为的层。
- 推翻既有架构决策时，必须在架构决策记录中说明理由；超出当前任务的架构缺陷应报告，
  不得借当前任务无授权地大规模重构。

依据：README 的工程结构、架构决策记录，以及本次会话提供的代理工程规则。

### V. 真实产品行为与证据验收

- 除明确要求原型或实验外，以正确、安全、可维护的生产行为为目标。
  按正确性、安全性、真实产品行为、架构和数据完整性、可维护与可验证性、最小合理变更的顺序取舍。
- 按变更范围验证真实入口、业务路径、状态变化、用户反馈、必要的持久化和错误恢复；
  测试替身只能证明其覆盖的工程链路，不得用假接口、占位数据或硬编码成功冒充产品能力。
- 运行与风险相称的最小充分验证，完成“实现、验证、检查、修复本次问题、重新验证”的闭环。
  目标验证充分后不无理由重复或扩大；不得降低有效断言、跳过失败或放宽验收门槛来制造通过。
- 工程检查、受控端到端测试、真实模型质量、实机行为和人工验收必须分别报告。
  已有阶段审查门槛必须遵守，前一阶段的测试通过不能代替下一阶段所需的明确放行。
- 只有实际行为已进入产品路径、适用验证通过、本次阻断问题已解决，且最终差异、工作区状态、
  剩余风险与人工验收边界均已核对和说明时，才能报告完成；否则如实报告需要审查、阻塞、部分完成或失败。

依据：本次会话提供的代理工程规则，以及架构与发布文档对工程证据和产品验收的区分。

## 技术与数据边界

- 延续 Electron、React、TypeScript、Tiptap、Yjs、SQLite 与现有工程工具链。
  具体版本、模型、阈值、性能目标和功能方案留在对应配置、架构记录或功能文档中，不在原则中冻结。
- 数据库结构变化沿用 Drizzle 生成迁移的流程；文档模型变化同步维护派生逻辑与对应格式版本。
  导入导出遵循现有 `.jiwei` 格式约定，分享时保持默认不携带版权资料原文件的边界。
- 现有许可证与第三方来源要求继续有效；发布、签名与安装验收按发布文档执行，
  不得将临时签名、构建成功或受控测试等同于正式签名、发布或真实安装验收。

## 开发、文档与 Git 工作流

- 开始工作前核对用户指定的项目根目录、分支、工作区状态和适用指令。
  用户指定独立工作树或只读范围时必须遵守；只获取当前任务所需上下文。
- 长期项目约束写入本文件；具体功能需求、方案、任务、评测指标和阶段结果写入相应功能文档。
  内部实施说明书、审查记录与计划沿用仓库外的内部文档存放规则，不纳入本代码仓库。
  后续使用 Spec Kit 功能流程时，必须明确设置 `SPECIFY_FEATURE_DIRECTORY` 指向该仓库外目录，
  并核对 `SPECIFY_INIT_DIR` 与当前项目一致；工具默认的 `specs/` 不能改变既有归档规则。
- 可共享的工程配置与长期原则可以纳入版本管理；密钥、个人环境、构建产物、本地指针与运行证据
  遵守现有忽略规则，不得强制加入被排除的内部资料。提交前检查差异与暂存范围，保留无关的未提交改动。
- 在当前任务授权内自主完成必要读取、修改、检查和直接相关修复，不为常规可逆工作反复请求批准。
  推送、合入主分支、重写历史、生产操作、不可逆删除和新增生产依赖，必须已有当前任务的明确授权；
  没有授权时，先准备可审查结果，再说明具体操作、影响和恢复方式以请求批准。
- 实施代理不自行创建发布仓库、上传或发布；沿用发布文档的 Claude 联合审查与用户最终发布边界，
  除非用户对当前任务另有明确授权。

## Governance

- 本文件汇总已有长期约定，不授权新增功能、部署或外部操作，也不替代具体功能文档和阶段审查记录。
  当前任务明确指令优先于通用工作流；安全、高风险及不可逆操作的授权边界必须保留。
  指令冲突、额外授权要求或可能偏离任务的规则，必须指出来源与冲突点，不得静默改写验收口径。
- 原则修订必须说明依据、规则变化及受影响的流程或文档；功能性需求不得通过修订原则代替需求分析。
  每次修订记录版本和日期：不兼容的规则删除或重定义升主版本，新增或实质扩充原则升次版本，
  不改变规则含义的澄清升修订版本。
- 方案评审与完成检查须核对适用原则、既有审查门槛和验证证据；偏离既有规则须明确记录，
  涉及尚未授权的边界时按现有授权规则处理，不得用“已生成文档”或“测试通过”宣称产品验收完成。
- 主要依据：[README](../../README.md)、[架构决策](../../docs/ARCHITECTURE.md)、
  [数据格式](../../docs/FORMAT.md)、[发布流程](../../docs/release.md)、
  [Git 忽略规则](../../.gitignore)，以及本次会话用户提供的 `AGENTS.md` 指令。
  建立本文件时，项目根目录未有实体 `AGENTS.md`；若后续新增，必须一并核对适用规则。
